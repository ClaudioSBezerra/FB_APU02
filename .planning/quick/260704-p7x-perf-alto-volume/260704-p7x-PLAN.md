# Quick Task 260704-p7x: Armazenamento e performance para alto volume (RFB + XMLs)

## Contexto

O módulo trabalha com grande volume de dados: apurações extraídas da Receita Federal
(rfb_requests/rfb_debitos/rfb_creditos) e documentos fiscais de compra e venda
(nfe_entradas, nfe_saidas, cte_entradas) importados via ERP Bridge (SAP S/4HANA) e
upload de XML. Análise dos caminhos quentes identificou quatro gargalos:

1. **Batch import linha-a-linha**: `erp_bridge_batch.go` faz `db.Exec` autocommit por
   documento + `upsertParceiro` avulso = 2 commits/fsync por doc. Lotes de milhares de
   notas pagam milhares de fsyncs.
2. **Refresh de MV em tempestade**: `REFRESH MATERIALIZED VIEW CONCURRENTLY
   mv_malha_fina_resumo` dispara a cada request de batch e a cada chunk de upload XML
   (4 call sites) — importações grandes recomputam a MV inteira dezenas de vezes em fila.
3. **`rfb_requests.raw_json` cresce sem limite**: JSON completo da apuração RFB fica
   para sempre na tabela quente.
4. **Índices/autovacuum faltando**: rfb_requests sem índice de listagem
   `(company_id, created_at)` nem índice parcial de status em andamento; autovacuum
   agressivo (migration 068) não cobre rfb_requests/rfb_creditos/parceiros.

## Tasks

### Task 1 — Migração 113: índices + autovacuum (aditiva)
- `113_perf_alto_volume.sql`:
  - `idx_rfb_requests_company_created` em `rfb_requests(company_id, created_at DESC)`
  - `idx_rfb_requests_em_andamento` parcial em `(cnpj_base, status)` WHERE status em
    ('pending','requested','webhook_received','downloading','reprocessing')
  - autovacuum scale factor 0.01/0.005 para `rfb_requests`, `rfb_creditos`, `parceiros`
    (mesmo padrão da 068)

### Task 2 — Batch import em transação única
- `erp_bridge_batch.go`: envolver o loop de documentos em `db.Begin()`;
  prepared statements (saída, entrada, CT-e, parceiro) preparados uma vez;
  `SAVEPOINT`/`ROLLBACK TO`/`RELEASE` por documento para preservar a semântica
  atual de erro-por-documento (conta erro e continua); commit único no fim.
- Falha no commit → HTTP 500 (bridge Python reenvia; upserts são idempotentes).

### Task 3 — Debounce do refresh da MV
- Novo `services/mv_refresh.go`: `RequestMVRefresh(db, view)` com coalescing —
  leading edge imediato, chamadas em burst colapsam num trailing refresh,
  cooldown de 2 min entre refreshes.
- Substituir os call sites dos caminhos de importação: `erp_bridge_batch.go` (1) e
  `xml_upload.go` (3). Ações manuais/admin (malha_fina.go, admin.go, limpeza_base.go)
  permanecem imediatas.

### Task 4 — Retenção opt-in de raw_json
- `services.StartRawJSONJanitor(dbFn)` (goroutine, tick 12h): se env
  `RFB_RAW_JSON_RETENTION_DAYS` > 0, `UPDATE rfb_requests SET raw_json = NULL`
  para requests `completed` com `updated_at` mais antigo que N dias.
  Desabilitado por padrão (env ausente/0) — sem perda de dados sem opt-in explícito.
- Registrar em `main.go` ao lado do StartRFBScheduler.
