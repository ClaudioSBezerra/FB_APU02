  <name>Task 1: Adicionar job test ao deploy-production.yml e ajustar needs</name>
  <files>.github/workflows/deploy-production.yml</files>
  <action>
  Editar `.github/workflows/deploy-production.yml` com TRES mudancas cirurgicas:

  1. Inserir um novo job `test` após o job `backup` e ANTES de `build-and-push`. Estrutura do job:
     - `runs-on: ubuntu-latest`
     - Sem `needs:` (roda em paralelo com `backup`)
     - Sem `if:` condicional — testes sempre rodam quando o workflow dispara (push em main, tag v*, workflow_dispatch). Isso é deliberado: defesa em profundidade.
     - Steps na ordem:
       1. `actions/checkout@v4`
       2. `actions/setup-go@v5` com `go-version: '1.22'`, `cache: true`, `cache-dependency-path: backend/go.sum`
       3. step com `name: Run Go tests`, `run: go test ./...`, `working-directory: backend`
       4. `actions/setup-node@v4` com `node-version: '20'`, `cache: 'npm'`, `cache-dependency-path: frontend/package-lock.json`
       5. step com `name: Install frontend deps`, `run: npm ci`, `working-directory: frontend`
       6. step com `name: Run frontend tests`, `run: npm test`, `working-directory: frontend`

     Usar `working-directory:` por step (não `defaults.run.working-directory`) para clareza — facilita debug quando um step falha. Ordem deliberada: Go tests primeiro (mais rápidos, sem `npm ci`); frontend depois (npm ci é o step mais caro).

  2. Alterar `build-and-push` (job existente):
     - `needs: backup` → `needs: [backup, test]`
     - Atualizar a condição `if`: `if: always() && (needs.backup.result == 'success' || needs.backup.result == 'skipped')` → `if: always() && needs.test.result == 'success' && (needs.backup.result == 'success' || needs.backup.result == 'skipped')`
     - O `needs.test.result == 'success'` é CRITICO: bloqueia o build se test falhar, mesmo com `always()`.

  3. Alterar `build-installer-images` (job existente):
     - `needs: backup` → `needs: [backup, test]`
     - Mesma atualização de `if:` do passo 2 — adicionar `needs.test.result == 'success'` à condição.

  NÃO alterar: `deploy-cliente-aws`, `notify`, nem qualquer step interno dos jobs de build. NÃO mover o job `backup` — ele continua independente porque backup de DB deve rodar mesmo que testes falhem (vai gerar artefato útil para investigação).

  Validar YAML após edição: estrutura indented corretamente, todos os jobs no nível `jobs:`, nenhum step sem `name:`. Rodar `python3 -c "import yaml; yaml.safe_load(open('.github/workflows/deploy-production.yml'))"` localmente.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| commit → CI runner | Qualquer push em main dispara o pipeline; testes rodam em ambiente ubuntu-latest do GitHub |
| CI runner → registry | Imagens só são publicadas se test passar — bloqueia regressão antes do registry |
| dev → produção | Testes em CI são a última linha de defesa antes do Coolify puxar a imagem |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-10 | Tampering | workflow bypass via `if:` mal configurado | mitigate | Condição `if: always() && needs.test.result == 'success' && ...` em production exige sucesso explícito de test; em staging usa `needs: test` simples (default behavior já bloqueia em falha) |
| T-04-11 | Information Disclosure | logs de test vazam dados | accept | Testes não usam dados reais (db=nil, payloads sintéticos); logs do runner GitHub Actions são visíveis apenas a colaboradores com permissão |
| T-04-12 | Denial of Service | flakiness em CI bloqueia deploys urgentes | mitigate | Tests são determinísticos (sem network, sem timing) — login_ratelimit usa Reset() para idempotência; nfe handlers só testam validações estáticas |
| T-04-13 | Elevation of Privilege | runner GitHub injetado com action maliciosa | mitigate | Usa apenas actions oficiais (actions/checkout, actions/setup-go, actions/setup-node) com versão major fixa (@v4/@v5) — sem actions third-party |
| T-04-14 | Repudiation | deploy sem teste passa silenciosamente | mitigate | Visibilidade do job `test` no grafo do Actions documenta cada run; falhas geram email automático aos colaboradores |
</threat_model>
