    // NUNCA expõe err.Error() ao cliente — previne vazamento de schema/query PostgreSQL (SEC-04).
    // Uso: sanitizeDBErr(w, http.StatusInternalServerError, "contexto da operação", err, "[HandlerName]")

        log.Printf("%s %s: %v", prefix, userMsg, err)
        jsonErr(w, status, userMsg)

<threat_model>
## Trust Boundaries

| Boundary | Descrição |
|----------|-----------|
| PostgreSQL → Go handler → HTTP response | Strings internas do banco não devem cruzar a fronteira para o cliente |
| Go log → Arquivo/stdout | Erros reais ficam apenas no servidor, nunca no browser |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-01 | Information Disclosure | http.Error(w, err.Error(), 500) | mitigate | Substituir por sanitizeDBErr que loga internamente e retorna mensagem genérica (SEC-04) |
| T-04-02 | Information Disclosure | jsonErr com concatenação de err.Error() | mitigate | Substituir por sanitizeDBErr — mensagem ao cliente nunca inclui erro real |
| T-04-03 | Information Disclosure | Nomes de tabela/constraint no body HTTP | mitigate | Coberto por T-04-01 e T-04-02 — err.Error() do lib/pq expõe schema PostgreSQL |
| T-04-04 | Tampering | Atacante usa schema exposto para construir ataques SQL | mitigate | Removendo exposição de schema via sanitizeDBErr elimina esse vetor de informação |
| T-04-05 | Repudiation | Erros de banco sem log antes da migração | mitigate | sanitizeDBErr garante log.Printf antes de toda resposta de erro de banco |
</threat_model>
